# 任务执行效率：度量方法与已落地优化

这份文档回答一个问题：**怎么让 ZSense 更快地把一个任务做完，以及凭什么说它变快了。**
原则只有一条——**先拿到每个环节的真实耗时，再决定改什么；改完必须再量一次，并把结论写进回归测试。**

## 一、为什么必须先量

两个真实的反例，都是在没有数字时最容易做的「想当然优化」：

| 看起来像瓶颈 | 实测结果 | 结论 |
| --- | --- | --- |
| 每轮都重发 16KB 工具模式，压缩描述一定很赚 | 工具描述合计只有 1898 字，压到极限也只省约 12%，而一轮模型往返是 10 秒级 | 放弃 |
| 运行游标文件已经 1.33MB，每次保存都全量重写 | 一次保存 1.2–2.8ms，对 10 秒级往返可忽略 | 只在文件体积上收口，不动写入策略 |

反过来，真正的大头往往藏在「大家默认它没问题」的地方：一次 55 轮的改表任务里，**569 秒中有 275 秒（48%）花在工具执行上，293 秒（52%）花在模型往返上**——于是所有优化都围绕「减少轮次」和「让工具并行」展开。

## 二、数字从哪里来

| 想知道什么 | 怎么量 |
| --- | --- |
| 一次任务模型时间和工具时间各占多少 | 读真实会话：`messages.agent_steps_json` 里每一步有 `durationMs`，`tools[]` 里每个工具有 `durationMs`，相加即可 |
| 每轮请求有多大 | 用本地 SSE 假模型跑一轮工具循环，统计 system / tools / messages 的字节数（`npm run bench:efficiency` 第 1 段） |
| 数据库读取路径慢不慢 | `EXPLAIN QUERY PLAN` 看有没有全表扫描和临时排序；再造规模数据（几百会话、几千消息）测真实耗时（第 2 段） |
| 启动慢不慢 | 计时 `new ZSenseDatabase()`、首次 `loadWorkspace()`、各服务构造（第 3 段） |
| 界面在长回答下卡不卡 | 看每个流式增量触发了多少次状态更新；逐 token 更新就是上千次整树重渲染 |
| 测试流水线多久 | `npm test` 会同时给出并行耗时和逐个串行的累计耗时 |

## 三、四个杠杆（按收益排序）

1. **轮次**：一轮就是一次完整模型往返。提示词要求把互不依赖的调用合并进同一轮、脚本自己完成「读取→修改→校验」并只打印一段摘要；第 12/24/36 轮及之后每 40 轮追加非终止性合并提醒。没有固定轮次硬上限，只有重复错误或重复工具结果的无进展保护；收尾轮若模型返回空内容，会自动再要一次结论。
2. **并行**：互不依赖的只读工具在同一轮真正并发（最多 4 个）；写入、终端、审批类工具形成依赖屏障，与之前所有调用串行，保证同一个文件的写入顺序；跨步骤的并行交给子 Agent（同一轮多个 `delegate_task`，默认 5 并发、每父级最多 5 个；自动计划仍最多 6 个任务，第 6 个等待空闲槽位）。
3. **热路径**：数据库查询走表达式索引；只读一个设置字段时不要加载整库消息；webhook 入站、Bot ID 校验同理。
4. **渲染**：流式回答按约 60ms 合并再更新状态；没有任何可见变化的状态更新直接返回原引用让 React 跳过渲染。

## 五、已落地优化

| 问题 | 证据 | 改动 |
| --- | --- | --- |
| 打开会话/每轮读历史都要全表扫描再临时排序 | `SCAN messages \| USE TEMP B-TREE FOR ORDER BY` | 表达式索引 `messages(conversation_id, datetime(created_at))` 等三个（索引表达式必须与查询里的 `datetime(...)` 完全一致才用得上），并清理早期加的无效索引 |
| 读一个设置字段却把全部会话、消息与 `reasoning`/`tool_events` JSON 读进内存（20 多处） | 0.05ms 对 82ms | 新增 `loadSettings()` / `loadGatewayConnections()` / `loadBotIds()` 轻量访问器并替换全部调用点 |
| 流式回答逐 token 触发整树重渲染 | 一次长回答上千次渲染 | `src/utils/stream-delta-buffer.ts` 按 60ms 合并；会话进度更新在无变化时返回原数组引用 |
| 流式回答同时刷新侧栏、Bot 工作区并反复启动平滑滚动 | token 到达时多个无关区域跟着渲染 | 运行中会话拓扑使用独立 revision；滚动合并进可取消的 `requestAnimationFrame` 并使用瞬时钉底 |
| 启动时解析全部页面与 MOSS 浏览器运行时 | 首屏 JS 1085.0KB | 聊天、设置、技能、模型、任务、Bot 工作区与首启页面按需加载；语音进一步改为轻量 MeloTTS 原生合成，不再携带 MOSS 浏览器 ONNX/WASM runtime |
| 前端依赖已进入 Vite 产物，又被 Electron 当生产依赖复制一遍 | `app.asar` 294.6MB，其中 `node_modules` 252.5MB | React、Univer、Markdown 等移到构建依赖；打包校验禁止它们重新进入 ASAR，`app.asar` 降至 76.4MB |
| 网关健康检查周期性重建完整 Workspace | 规模库约 96.8ms / 次 | 新增 `loadGatewayRuntime()`，只读 Bot 状态、网关连接和设置，约 0.05ms / 次 |
| 局域网 Web 读取大 JS/CSS 时同步阻塞主进程 | 表格编辑器单文件约 6.8MB | 静态文件改为流式读取，文本资源按浏览器能力使用 Brotli/Gzip，hash 资源使用 immutable 缓存 |
| Excel 每个单元格变化都序列化整本工作簿 | 大表输入可见卡顿 | 仅 Univer 返回样式 ID 时才按需序列化一次样式表 |
| 已完成后台进程及输出永久驻留 | 单进程最多约 2MB 输出和完整 ChildProcess 引用 | 完成后释放子进程对象，只保留最近 24 条已结束记录 |
| 搜索误入打包产物和离线工具 | `release/dist/bundled-tools` 可达数 GB | 工作区搜索和回滚点跳过构建产物、缓存、覆盖率及离线工具目录 |
| 收尾轮空内容要用户手动催 | 兜底文案要求用户发「继续汇总」 | 自动再要一次结论，两次都空才回落提示 |
| 已结束运行的游标保留全部步骤，文件随运行次数无限增长 | 1.33MB 里 798KB 是历史步骤 | 结束后只保留末尾 8 步 |
| 42 个测试只能逐个手工跑 | 串行 38.7s | `npm test` 并行入口（并发池 + 单项超时 + 失败日志尾部），24.6s |

## 六、测过但不值得改

- **压缩工具模式**：见第一节，只省约 12%，且会削弱工具说明的可读性。
- **启动流程**：数据库打开 2ms、首次快照 29ms、服务构造 0ms，没有优化空间。
- **游标保存策略**：一次 1.2–2.8ms，不值得为它引入节流可能带来的恢复精度损失。
- **工作区列目录**：已有深度与条数上限；搜索另外排除了构建产物、缓存和离线工具目录。
- **收尾前自动只读核对**：实现过——任务真的改过东西（写文件 / 执行命令 / 对外提交）时，模型给出最终回答后自动补一轮 `tools: []` 的核对（结论作为最终回答，界面显示 `verifying` 状态与 `verified` 步骤，见提交 `d0715e5`）。**已按用户要求撤掉**（提交 `1f432e7`）：模型在干活时自己回读确认的那一步已经是检查，再强制加一轮等于每次写操作都多花一次模型调用，收益不明显。要重新加回来之前先确认用户是否真的需要"系统级强制核对"。

## 七、回归保护

- `npm run test:efficiency`：热点查询必须走索引（且不再临时排序）、`loadSettings()` / `loadGatewayRuntime()` 必须显著快于完整快照、`electron/` 下不允许再出现 `loadWorkspace().settings` 这类整库读取、渲染层必须使用真实行为验证过的增量合并、测试入口必须带递归保护。
- `npm test`：46 个测试一次跑完；任何一项退化都会直接变红。
- `npm run verify:packaged`：校验主进程运行时依赖、禁止前端库重复进入 ASAR、限制 ASAR 体积，并确认 macOS 只保留中英文资源。
- `npm run bench:efficiency`：优化前后各跑一次，对比上面的基线数字。

## 八、怎么重新测量

```bash
npm run bench:efficiency                          # 全量（请求体量 + 规模数据 + 启动）
npm run bench:efficiency -- --quick               # 只测启动
npm run bench:efficiency -- --conversations 500 --messages 10   # 更大的规模数据
```

规模数据写入与查询都发生在临时目录，不会碰真实用户数据；启动一段会复制真实库来测，也只读副本。

## 九、离线语音磁盘瘦身（2026-10-10，本机 0.26.10）

此项衡量文件字节数，不是运行内存。MOSS-TTS 与浏览器 ONNX/WASM 链路换成 MeloTTS 固定中文音色，Whisper Base 换成 Q5_1；模型、原生运行库和许可证仍随应用部署，首次使用不下载组件。

| --- | --- | --- |

移除可重新获取的旧语音模型与 WASM，不删除用户音色历史、会话或配置；本轮下载/解压缓存验收后清理。旧安装包不在此次清理范围。本轮只替换本机 `.app`，不改版本、不生成安装包、不发布。

验收：`npm test` 59 项通过；类型检查、构建、`verify:packaged`、真实中文合成/量化识别、当前与排队播报取消、退出时 TTS/STT 进程与临时音频清理通过。设置页使用隔离 Chromium 验证试听、停止、错误重试、小窗口和语种扩展入口。
